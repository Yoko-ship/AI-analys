# §3.11 — AI-анализ новостей и информационного поля: скоуп-документ

**Дата:** 2026-07-09
**Статус:** проектирование (реализация не начата — по решению пользователя это единственный крупный блок, взятый в планирование).
**Контекст:** ТЗ §3.11 + §3.4 (новостной фон в risk profile) + §3.10 (уведомления о новостных всплесках).

---

## 1. Что есть сейчас (факт из аудита кода)
- **Пайплайна сбора новостей нет.** Нет коллектора, таблицы, списка источников, датасета.
- Единственное «новостное» — **live-поиск LLM во время анализа**: `analyzer.py:2126-2146` (Haiku web search «Ищу новости-катализаторы») и `bot.py:505`. Это генеративный per-request поиск, не хранимый сбор.
- `analysis_service.py` трактует `news` как **обычно пустой input-слот** — модели велено писать «Нет данных в текущем наборе», если новости не переданы (`:80-81,98`).
- Следствие: **информационное измерение risk profile (§3.4) и новостные уведомления (§3.10) заблокированы** до появления этого модуля.

## 2. Требования ТЗ §3.11 (чек-лист)
Модуль должен:
- анализировать новости, информационный фон, влияние на рынок, тональность, информационные риски;
- **определять**: эмитента, отрасль, инструмент, ключевые сущности;
- **классифицировать** новости (финотчётность / корпсобытие / регуляторика / рыночная ситуация);
- **выявлять**: всплески публикаций, синхронные публикации, медиа-атаки, аномальную информационную активность (4 независимых детектора, параллельно);
- все выводы — **статистический факт, не диагноз** («выявлена аномальная активность» ≠ «компанию атакуют»); обязательный дисклеймер; срабатывания в лог + могут триггерить уведомления.

## 3. Архитектурная привязка к существующему проекту
Проект уже устроен как **collector-push → prod-serve** (openinfo блокирует IP Railway, коллектор гонится локально и пушит через `/api/admin/*`). Новостной модуль должен встроиться в ту же модель:

```
[news collector (локально/UZ-хост)]
   ├─ fetch источников (RSS/HTML/Telegram/openinfo disclosure)
   ├─ dedupe + нормализация
   ├─ entity resolution (эмитент/отрасль/инструмент)  ← переиспользовать entity_resolver.py
   ├─ классификация типа новости (LLM/правила)
   ├─ тональность (позит/нейтр/негатив) на новость   ← ML/LLM-модуль
   └─ push → POST /api/admin/news  (по образцу /api/admin/facts)
[prod API]
   ├─ хранит news + tone + type + entities
   ├─ GET /api/news, GET /api/news/{ticker}          (публичный: лента; §3.2 п.6)
   ├─ агрегаты: тональность за период, динамика, темы  (закрытый контур; §3.11)
   └─ 4 детектора аномалий (по расписанию/на push)     → лог + триггеры уведомлений
[frontend]
   ├─ публичная лента «Новости» (§3.2)
   └─ на карточке эмитента: тональность фона + инфо-риск (закрытый контур)
```

Переиспользуемое: `entity_resolver.py` (тикер↔ISIN↔имя), `facts`-паттерн хранения, `/api/admin/*` push-плюмбинг, `company_catalog`/`COMPANY_SECTORS` для отрасли.

## 4. Источники (конфигурируемый список — ТЗ требует отдельной конфигурации)
Кандидаты для РУз/UZSE:
- **openinfo disclosure** (существенные факты) — уже частично доступно, сейчас берётся только dividend-calendar; расширить на материальные факты.
- Сайт **РФБ «Тошкент»** (новости биржи, листинг/делистинг).
- Деловые СМИ Уз (Spot.uz, Kun.uz, Gazeta.uz, Review.uz и т.п.) — RSS/HTML.
- Telegram-каналы (официальные каналы эмитентов/регулятора) — через Bot API/парсер.
- Пресс-релизы эмитентов (офиц. сайты).
> Список выносится в конфиг (`news_sources.json`), с полями: url, тип (rss/html/tg), вес охвата (для взвешенной агрегации тональности — ТЗ §3.3 «агрегация взвешенная по охвату источника»).

## 5. Компоненты и алгоритмы
| Компонент | Подход MVP | Подход «полный» |
|---|---|---|
| **Сбор** | RSS + HTML-парсеры, cron в коллекторе | + Telegram, + очередь, + инкрементальный dedup по URL/хэшу |
| **Entity resolution** | правила: поиск тикера/имени по `entity_resolver` словарю | NLP NER (сущности: суммы, персоны, даты, гео) |
| **Классификация типа** | ключевые слова → 4 класса | LLM-классификатор с few-shot |
| **Тональность** | LLM per-новость (позит/нейтр/негатив) + кэш | отдельная ML-модель (fine-tune), калибровка |
| **Агрегация фона** | среднее тональности за период, взвешенное по охвату | + динамика (лучше/хуже/стабильно), ключевые темы (кластеризация) |
| **Детектор всплеска** | кол-во публикаций/день vs скользящее среднее за 90 дней (>2σ) | адаптивные пороги по эмитенту |
| **Детектор синхронности** | ≥N источников со схожим текстом в окне T (шингл/симхэш) | семантическая близость эмбеддингами |
| **Детектор медиа-атаки** | всплеск + доминирование негатива из многих источников | + оценка охвата/координации |
| **Детектор аномалии** | любой паттерн вне историч. нормы эмитента | ML поверх рассчитанных признаков |

Все 4 детектора — **статистические, независимые, параллельные**. Вывод — факт + окно времени + величина отклонения; формулировки без «атака/манипуляция» без явных оснований (ТЗ).

## 6. Модель данных (эскиз)
`news` (по образцу `facts`): `id, url(hash unique), source, published_at, title, body, lang`.
`news_entities`: `news_id, ticker, sector, instrument, relevance`.
`news_nlp`: `news_id, tone(pos/neu/neg), tone_score, type(4 класса), entities_json`.
`news_signals` (срабатывания детекторов): `ticker, detector, window_start, window_end, magnitude, created_at`.

## 7. Интеграция с остальным ТЗ
- **§3.2 п.6 Новости** — публичная лента (факты, без прогноза). Разблокируется сразу после MVP-сбора.
- **§3.4 risk profile → информационное измерение** — из `news_nlp` + `news_signals` (Низкий/Средний/Высокий). Разблокирует полный 3-мерный risk profile (backend уже спроектирован под это в TRANCHE C).
- **§3.10 уведомления «новостной всплеск»** — триггерятся из `news_signals` (когда движок уведомлений будет в объёме).
- **§3.6 comparative / §3.11 тональность по отраслям** — агрегаты по сектору.

## 8. Фазировка
- **Фаза 0 (разблокировка ленты):** сбор из 3-5 источников + entity resolution + хранение + `GET /api/news` + публичная лента. *(≈ средняя, данные+инфра)*
- **Фаза 1 (тональность):** LLM-тональность per-новость + агрегация фона + отображение на карточке эмитента (закрытый контур).
- **Фаза 2 (детекторы):** всплеск + синхронность → `news_signals` → информационное измерение risk profile.
- **Фаза 3 (полный):** медиа-атака + аномалии, ML-тональность, темы/кластеризация, взвешивание по охвату.

## 9. Риски / ограничения
- **openinfo IP-блок** — новостной коллектор так же гонится вне Railway и пушит (как финансовый). Никакого сбора на prod.
- **Качество источников Уз** — мало структурированных RSS; много HTML-парсинга (хрупко). Список конфигурируемый, чтобы чинить точечно.
- **Telegram** — нужен доступ к каналам (Bot API ограничен; парсер каналов — серые зоны).
- **Тональность на узбекском/русском** — LLM справляется, но специализированная ML-модель (ТЗ упоминает «отдельный ML-модуль») — отдельный трек с разметкой.
- **Комплаенс** — только факты, обязательный дисклеймер, без «атака/манипуляция» без оснований.
- **Стоимость LLM** — тональность per-новость масштабируется по объёму потока; кэш по хэшу + батч.

## 10. Рекомендация
Начать с **Фазы 0 + Фазы 1** (лента + тональность) — это закрывает публичный п.6 «Новости» и даёт вход для информационного измерения risk profile, при умеренных затратах. Детекторы (Фазы 2-3) — после, когда накопится история для статистических порогов (всплеск считается против 90-дневной нормы, т.е. нужно ≥90 дней сбора).
